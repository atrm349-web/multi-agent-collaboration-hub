## 第八轮：DS-03 中断与恢复实测（2026-11-09 14:50–14:57）

三个场景，两种走法，一个真缺陷：

| 场景 | 结果 |
|---|---|
| A 正常停止（SIGINT，测试执行中） | ✅ 干净：任务/子任务 cancelled、槽位释放、子进程回收、重启无残留 |
| B 控制器崩溃（SIGKILL，测试执行中） | ❌ **任务永久卡死**：task=running、IMPL=validating、error=null、slot=0、live=true；没有 interrupted 记录，ack 接口用不上；崩溃时两个测试进程仍在跑 |
| C 模型进程被杀（SIGKILL 进程组，走 codex CLI 才有真实子进程） | ✅ 收敛：run failed / PROCESS_CRASHED、子任务 failed、任务 failed、槽位释放；但**不会自动重试**（retryable=false） |

B 的根因很清楚：`reconcileExpired` 只扫 `run.status ∈ (starting, running, cancelling)`，而这次中断发生在**测试阶段**——测试阶段没有自己的 run/claim，所以对账逻辑根本看不见它。

**已实测的唯一出路**：人工 `POST /tasks/{id}/cancel` → 202 → 3 秒后 task/subtask 全部 cancelled。

**给 Codex 的三条最小修复**（按代价排序）：
1. 启动时补一次"孤儿 validating"对账（子任务 validating + 无活跃 claim → 标 failed/PROCESS_CRASHED 并释放槽位）；
2. 让测试阶段也有自己的 claim（含测试进程组 pid），崩溃后可被统一对账；
3. `meta` 暴露 `stuckValidating`/`needsAttention` 计数，让 UI 能提示。

**结构性说明**：API 型 provider（DeepSeek/Gemini）的 `claim.process_group_id` 记录的是**控制器自己的 pid**（`deepseek/runtime.ts` 里 `onSpawn(runId, process.pid)`），所以"进程组已验证停止"对它们而言只代表旧控制器不在了；测试子进程不在 claim 里，这正是 B 卡死的另一个根因。

详情与复现：`DS-03/live/报告.md`；证据：`DS-03/live/evidence/{A,B,C}.{log,json}`、`B-manual-cancel.json`。
