- 证据：`evidence/store.ts.patch`、`evidence/hub.ts.patch`；成对运行日志 `DS-03/live/evidence/B-before-fix.{log,json}` 与 `B-after-fix.{log,json}`

## 一、补丁内容（两处，共 ~45 行）

### 1. `packages/core/state/store.ts` — 新增启动期对账

```ts
reconcileInterruptedValidations(): string[]
```

它找出**满足全部三条**的子任务：

1. `status = 'validating'`；
2. 该子任务的最新 run **已终态**（不是 starting/running/cancelling）；
3. 没有任何活跃 run 指向它。

然后把它们标成 `failed`（`error.code = PROCESS_CRASHED`，message 明确写"validation was interrupted；retry 前先检查工作区"），并把对应任务标 `failed`、清掉可能残留的执行槽。

**只在控制器构造时调用一次**——那时本进程还没有任何本地任务，所以不可能误伤正在跑的验证。

### 2. `packages/core/hub.ts` — 启动时调用一次

```ts
// Startup-only: a crash during the validation phase leaves subtasks in
// "validating" with no active run, which reconcileExpired cannot see.
try { store.reconcileInterruptedValidations(); }
catch (error) { console.error("[hub] interrupted-validation sweep failed", String(error).slice(0,200)); }
```

失败只记日志，不影响启动（不让对账把服务带崩）。

## 二、验证方式

完全复刻 DS-03 场景 B：模型跑完后进入 45 秒注册测试窗口 → `SIGKILL` 控制器 → 立即重启 → 等 13 秒（lease 10 s）→ 读数据库。

## 三、结果对比

同一注入、同一时刻读库，成对日志：

```
修复前: task=[{"s":"running","e":null}]   subs=[{"c":"IMPL","s":"validating"}]  slot=0 live=true
修复后: task=[{"s":"failed","e":"PROCESS_CRASHED"}] subs=[{"c":"IMPL","s":"failed"}] slot=0 live=true
```

| | 修复前（共享代码） | 修复后（副本 + 补丁） |
|---|---|---|
| `task.status` | `running`，`error=null` | **`failed`，`error=PROCESS_CRASHED`** |
| `IMPL.status` | `validating`（永久） | **`failed`** |
| `slot` | 0 | 0 |
| `liveExecutionAvailable` | true | true |
| 能否自愈 | ❌ 只能人工取消 | ✅ 重启即明确失败，可直接 retry / 排查 |

复现两遍（未修复时）都停在 `running/validating`；打补丁后一次就变成 `failed/PROCESS_CRASHED`。

## 四、这个补丁**不解决**的事（要写清楚，别当成万能修复）

1. **不杀孤儿测试进程**。崩溃那一刻的 `codex sandbox` 包装与测试脚本仍会继续跑到自然结束——因为测试阶段**没有自己的 claim**，系统不知道它们的存在。要彻底解决需要"测试阶段也写 claim"（我在 DS-03 报告里的第 2 条建议）。
2. **不自动续跑**。它只把状态从"静默卡死"变成"明确失败"，符合现有"不盲目续跑"的策略。
3. **不处理"验证完成但结果没落盘"的极小窗口**（测试刚结束、写库前崩溃）：那时子任务可能仍是 `validating`，补丁会把它标 failed 而不是"按测试结果收尾"。这是有意的保守选择。

## 五、建议的落地顺序

1. 先合这个补丁（小、只影响启动路径、有对照实验）；
2. 再把"测试阶段 claim + 进程组"补上（能一并解决孤儿进程与"能不能确认它停了"）；
3. UI 侧把 `failed(PROCESS_CRASHED)` 显示成"需要人工检查"的明确提示，而不是普通失败。
