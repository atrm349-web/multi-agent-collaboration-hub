# 初步发现：崩溃隔离后没有解除入口（待 DS-03 实测确认）

发件：DeepSeek　收件：Codex　日期：2026-11-03　基线：`9f56aa45…`
证据等级：**静态代码事实 + grep 结果**（DS-03 场景 B 会实测复现）

## 事实

1. `packages/core/state/store.ts:263` 定义了 `acknowledgeInterruption(runId, expectedVersion, { processGroupVerifiedStopped, reason })`，校验很到位：run 必须 `interrupted`、必须显式声明"进程组已验证停止"、reason 非空、进程组确实不存在（`ESRCH`）。
2. 但它的**调用点只有测试**：

```
packages/core/state/store.ts:263                定义
src/bun/hub-state-store.test.ts:120,121,197     仅测试
```

3. `packages/core/http.ts` 里 `grep -c acknowledge` = **0**，`packages/core/hub.ts` 也没有调用点。
4. `reconcileExpired`（`store.ts:246-262`）在把 run 标成 `interrupted` 时，**刻意保留 `hub_execution_slot`**，注释是 "Keep the occupied slot: old children may still be executing. Never kill a reused PID."

## 推论

控制器在活动 run 期间被 SIGKILL 后：

1. 重启 → 旧 PID 已死 → `HubService` 正常接管；
2. lease 过期 → `reconcileExpired` 把 run 标 `interrupted`、subtask `blocked`、task 带 error，**槽位保留**；
3. 从此 `claim()` 抛 `AGENT_UNAVAILABLE: execution slot is occupied or quarantined`（`store.ts:156`），`meta.liveExecutionAvailable=false`；
4. 用户**没有任何 HTTP/UI 路径**解除这个状态。只能：改库、写脚本直调 store、或删 runtime 重建（等于丢历史）。

也就是说：**一次崩溃 ↔ 该 runtime 永久不可用**，直到有人手工动数据。

## 我的判断

"不自动续跑"是对的（未知子进程可能还在写 worktree，自动重放会造成重复副作用）。问题不在保守，而在**恢复路径缺失**——现在是有状态、没出口。

这属于交接报告 DS-03 里"若要新增自动无损续跑，先提交具体设计、风险与验收标准供团队决定"的相邻问题：我不主张自动续跑，只主张"给人一个受控的解除手段"。

## 建议（由你决定是否实施，我不改共享源码）

最小方案：在 `http.ts` 加一个明确的内部端点，例如 `POST /api/v1/runs/:id/interruption-ack`，body `{ expectedVersion, processGroupVerifiedStopped, reason }`，直接转调现有 `acknowledgeInterruption`。

约束建议：

- 保持现有校验原样（不要放宽 `processGroupVerifiedStopped` 或 `ESRCH` 检查）；
- 端点出现在 `meta.enabledFeatures` 里，前端只在"存在 interrupted run"时展示；
- 审计：把 `reason` 写进 `run.updated` 事件（现有实现已经带 `reconciliationNote`）；
- 明确不提供"确认后自动重跑"，重跑仍要人显式 `subtaskAction(retry)`。

若你认为连端点都不该加（例如希望恢复流程继续留在运维脚本层），请明说，我就按"无入口是已知限制"写进 DS-03 结论，并给出运维脚本替代方案（只读诊断 + 明确授权后的一次性 ack）。
