# DS-03 验证方案：活动任务中断与恢复

- 提出方：DeepSeek　日期：2026-11-03　状态：**方案（待 DS-02 之后执行）**
- 基线：`backend/agetor` `9f56aa45…`
- 纪律：所有故障注入**只针对本次自建的临时进程与临时仓库**（`DeepSeek/DS-03/…` 内），不碰共享目录、不碰用户仓库、不碰未知进程。

## 1. 要证明的事

| # | 场景 | 要证明 |
|---|---|---|
| A | 正常控制器停止（SIGINT） | 受控停止会把活动任务收敛到 `cancelled`，不留下孤儿进程与占用的执行槽 |
| B | 异常控制器退出（SIGKILL） | 重启后 lease 过期被发现，run 标 `interrupted`、subtask `blocked`，**同一 attempt 不被重复派发**，未知进程不被误杀 |
| C | 活动模型进程退出 | 模型侧崩溃表现为 run 失败，任务按 `retryable` 规则返工或终止，状态一致不悬空 |

## 2. 代码事实（源码实读，DS-03 的判定依据）

| 机制 | 位置 | 行为 |
|---|---|---|
| lease | `store.ts:33` | 默认 `leaseMs=10_000`；心跳间隔 `max(25, leaseMs/3) ≈ 3333 ms`（`durable-codex.ts:46-56`） |
| 过期对账 | `store.ts:246-262` | 只处理 `starting/running/cancelling` 且 lease 过期的 claim：run→`interrupted`、subtask→`blocked`、task 写入 `error`；**刻意保留执行槽**（"old children may still be executing"） |
| 解除隔离 | `store.ts:263-281` | `acknowledgeInterruption` 要求 `processGroupVerifiedStopped === true` 且进程组已不存在（`ESRCH`），否则拒绝；成功后释放槽位与 agent |
| 不重放 | `durable-codex.ts:11`、`store.ts:157` | 新 runner 不会重放旧 claim；`(subtask_id, attempt)` 已有 claim 就拒绝再次 claim |
| 单并发 | `store.ts:156` | 执行槽被占用时 `AGENT_UNAVAILABLE`，`meta.liveExecutionAvailable=false` |
| 控制器接管 | `hub.ts:80-89` | 旧 owner PID 仍活着 → `AGENT_UNAVAILABLE`；已死 → 接管，并把遗留 `pending` 请求标 `PROCESS_CRASHED` |
| 正常停止 | `hub.ts:412-416` | 活动任务转 `cancelling` → 取消 run → 等 promise → `finishControl` 收尾并删除 owner 行 |

**关键推论**：控制器被 SIGKILL 后，平台**故意不自动续跑**——它把运行隔离起来，等人确认进程真的停了、副作用已看过，才释放槽位。DS-03 要验证的正是"这种保守恢复是否正确"，而不是"能不能一键续跑"。

## 3. 实验环境

复用 DS-02 的仓库与夹具，新增一个"慢验收"配置：

```
DeepSeek/DS-03/
  A-normal-stop/    repo（复制 DS-02 repo）、owner-tests/slow.mjs、config.json（port 4323）
  B-controller-kill/
  C-model-exit/
  evidence/
```

`slow.mjs`：先 `sleep 40`，再跑 DS-02 的 5 条断言。用意：让"活动窗口"足够长，使中断注入点确定、可复现，而不是赌模型跑多久。

- A/B 在中**测试阶段**注入（模型只需 1 次真实调用即可进入测试阶段）。
- C 在中**模型阶段**注入（需要一次较长输出的真实调用；用"写 120 行说明文档"这类任务拉长窗口）。

成本：A、B 各 1 次真实调用；C 1 次（可能需重试一次）。总计约 3–4 次，远低于 DS-02。

## 4. 场景步骤

### A. 正常控制器停止

1. 起服务（4323），建任务，等到 `run.status=running` 且 `subtask.status=validating`（测试阶段）。
2. 记录：run id、claim 的 `process_group_id`、`hub_execution_slot` 内容、`hub_ws` 目录、task/subtask 版本。
3. 给控制器发 SIGINT，等进程退出（`kill -0` 失败 + 4323 无监听）。
4. 断言：
   - task `cancelled`、subtask `cancelled`（`finishControl`），approval 无 pending；
   - `hub_execution_slot` 为空；
   - 测试子进程已回收（`kill -0 <pgid>` 失败，SIGTERM→SIGKILL 升级已生效）；
   - **原仓库 HEAD 不变**。
5. 重启服务：不应出现 `interrupted`/`blocked` 残留；`meta.liveExecutionAvailable=true`。

### B. 异常控制器退出（SIGKILL）

1. 同 A 的进入方式（测试阶段，进程组已存在）。
2. `kill -9` 控制器 PID（**只杀控制器，不杀模型/测试进程组**——这正是要验证的"未知进程不被误处理"）。
3. 记录：控制器消失时刻、`kill -0 <pgid>` 仍成功（子进程活着）。
4. 立刻重启控制器（同一个 runtime root）：
   - 期望：启动时 `HubService` 接管（旧 PID 已死），`DurableCodexRunner` 构造调用 `reconcileExpired()`；但**lease 还没过期**（10 s），所以第一次对账可能什么都没做。
   - 等待 > 10 s 后（心跳已停），对账应把 run 标 `interrupted`、subtask `blocked`、task 带 `error`。
   - 断言：**没有新建 run**（run 数量不变）、**没有重新 spawn**（进程组 PID 不变）、`meta.liveExecutionAvailable=false`（槽位仍被占）。
5. 尝试 `acknowledgeInterruption`（用 DB 里 run 的 version）：
   - 子进程还活着时**必须被拒**（`AGENT_UNAVAILABLE: process group is still present`）；
   - 杀掉子进程（`kill -9 -<pgid>`）后再试，**必须成功**，槽位释放、agent 恢复 available、事件 `run.updated` 带 `reconciliationNote`。
6. 结论口径：正常停止的"孤儿进程"是否真的被清理？如果第 2 步的子进程在控制器死后**继续写 workspaces**，要记录它写了什么（这是"崩溃后工作区可能被污染"的直接证据）。

### C. 活动模型进程退出

1. 起任务，等到 `run.status=running` 且日志里出现 `thread.started`（session 已建立）。
2. 从 claim 取 `process_group_id`，`kill -9 -<pgid>`（只杀本次的模型进程组）。
3. 记录 run 终态：`exitCode`、`error.code`（`retryable` 与否）、subtask 状态、是否触发 `rework`（attempt 2）。
4. 若触发返工：等 attempt 2 完成，验证状态机继续推进（不悬空）；
   若直接失败：验证 task `failed` 且 `error` 明确、无 pending 审批、无残留槽位。
5. 重启服务再确认一次状态稳定（无 `interrupted` 残留）。

## 6. 已知约束（提前声明，避免把环境限制写成产品缺陷）

1. 我的沙箱**禁止 `ps`**。进程存活只能用 `kill -0 <pid>` + DB 里记录的 PID + 短时间窗三者交叉；PID 复用风险靠"注入与检查间隔 < 30 s"控制。若你需要 `ps` 级证据，请在你的 Terminal 里补一条 `ps -o pid,pgid,command -p <pid>`。
2. 场景 B 的"重启后第一次对账可能什么都不做"是 **lease 10 s** 决定的，不是 bug。我会等足 15 s 再断言，并把这个时间点写进报告。
3. `acknowledgeInterruption` **没有 HTTP 路由**（`http.ts` 里没有对应端点），DS-03 只能通过脚本直接调用 store 方法或直接读库判断。这本身是一条产品缺口：**用户无法从 UI 解除隔离**，只能等或重启进程。建议由 Codex 评估是否补一个受控的内部端点（明确标注影响面），我不会擅自加。
4. 场景 C 的"模型进程退出"在我的执行环境里等价于对 CLI 子进程组发 SIGKILL；真实网络中断/CLI 自身崩溃不在本轮范围。

## 6.5 静态发现（待 DS-03 实测确认）：隔离后没有解除入口

`acknowledgeInterruption`（`store.ts:263`）目前**只被测试调用**：

```
packages/core/state/store.ts:263                定义
src/bun/hub-state-store.test.ts:120/121/197     仅测试调用
```

`packages/core/http.ts` 里没有任何端点（`grep -c acknowledge` = 0），`hub.ts` 也没有调用点。

结合"`reconcileExpired` 刻意保留执行槽"（`store.ts:259`），推论是：

> 一旦控制器在活动 run 期间被 SIGKILL，该 runtime 的执行槽会**永久被占用**：`claim()` 抛 `AGENT_UNAVAILABLE`，`meta.liveExecutionAvailable` 永远 false，除非有人绕过 HTTP 直接调用 store 方法或改库。

这不是"保守恢复"本身的问题（不自动续跑是对的），而是**恢复后没有可用的解除手段**。DS-03 场景 B 会实测确认这一点；如果确认，建议的最小修复是给 Codex：一个受控的内部端点（或启动时的显式人工确认参数），要求同时满足"进程组已验证停止 + 操作者写明 reason"，且不改变现有 `acknowledgeInterruption` 的校验逻辑。是否实现由 Codex 决定，我不会擅自加。

## 7. 判定标准

- A 通过：无孤儿进程、槽位释放、仓库不变、重启干净。
- B 通过：run 恰好一次 `interrupted`（不重复）、subtask `blocked`、不重复派发、未确认前不能继续执行、确认后槽位正确释放。
- C 通过：run 终态明确（`failed` 或返工）、无 `interrupted` 残留、无悬空 task。
- 任一不满足 → 记录为**问题**并给出最小修复建议（不直接改共享源码）。
