# DS-03 中断与恢复实测报告

- 执行：DeepSeek　时间：2026-11-09 14:50–14:57 JST　基线：`集合agent/backend/agetor` HEAD `0ce7323`
- 方法：自建 `duration-kit` 仓库 + **45 秒"慢验收"脚本**（`owner-tests/slow.mjs`），把活动窗口固定下来，再在确定的时刻注入故障。所有故障只针对本次脚本自己启动的进程。
- 证据：`evidence/A.{log,json}`、`B.{log,json}`、`B-manual-cancel.json`、`C.{log,json}`

## 一、结论

| 场景 | 注入点 | 结果 |
|---|---|---|
| A 正常停止（SIGINT） | 注册测试执行中 | ✅ **通过**：任务/子任务全部 `cancelled`、执行槽释放、子进程被回收、重启后无残留 |
| B 控制器崩溃（SIGKILL） | 注册测试执行中 | ❌ **缺陷**：任务**永久卡在 `running` / 子任务卡在 `validating`**，没有 `interrupted` 记录、没有错误、`liveExecutionAvailable` 仍为 true，只能人工取消 |
| C 模型进程被杀（SIGKILL 进程组） | 模型调用进行中 | ✅ **收敛**：run `failed` / `error.code=PROCESS_CRASHED`、子任务 `failed`、任务 `failed`、槽位释放；**不会自动重试** |

## 二、场景 A：正常停止（通过）

```
05:50:57 hub 启动，建任务
05:51:21 模型完成，进入注册测试窗口（subtask=validating）
05:51:23 SIGINT
→ task=cancelled，IMPL/FINAL-REVIEW 均 cancelled，执行槽=0，测试子进程已不存在
→ 重启：liveExecutionAvailable=true，interrupted run 数=0
→ 原仓库 HEAD 未变、工作区干净
```

**这是一条干净路径**：`close()` 会 abort 当前测试、等 promise 收尾，再把 pausing/cancelling 收敛成终态。

## 三、场景 B：崩溃发生在"测试阶段" → 任务卡死（核心发现，**复现两次**）

```
05:52:53 进入注册测试窗口（subtask=validating，测试进程 7709/7713 在跑）
05:52:54 SIGKILL 控制器
          → claim 里记录的 process_group_id 是控制器自己的 pid（已死）
          → 真正在跑的两个测试进程（codex sandbox 包装 + slow.mjs）**仍在运行**
05:52:54 重启控制器，等 13 秒（lease 10 s 早已过期）
→ runs = [succeeded]        ← 模型那一步早就成功了，所以不会被判 interrupted
→ subtask IMPL = validating ← 永远停在这里
→ slot = 0，liveExecutionAvailable = true
→ task.status = running，error = null，progress = 0
```

**为什么 `reconcileExpired` 没有处理它**：它只扫描 `status in (starting, running, cancelling)` 的 run。本例里 run 已经 `succeeded`，被中断的是**测试阶段**，而测试阶段在数据库里没有自己的 run/claim，所以对账逻辑根本看不到它。

**后果**：

1. 任务永远"运行中"，进度 0，无错误——UI 上看起来像还在跑；
2. `slot=0` 且 `live=true`，调度器认为可以接新任务，但这个任务永远占着 `IMPL` 的 `validating`；
3. 没有任何自动恢复路径；`acknowledgeInterruption` 也用不上（没有 `interrupted` 的 run）；
4. 崩溃时那两个测试进程还活着——它们的输出管道已经断了，结果永远没人收。

**复现性**：同样注入跑了两遍（05:52 与 05:57 两次），两次都停在完全相同的状态：`task=running / error=null`、`IMPL=validating`、`runs=[succeeded]`、`slot=0`、`live=true`、崩溃时各有 2 个孤儿测试进程（`codex sandbox` 包装 + `slow.mjs`）。这不是偶发。

**唯一出路（已实测）**：人工取消。`POST /api/v1/tasks/{id}/cancel` 返回 202，3 秒后 `task=cancelled`、两个子任务 `cancelled`。见 `evidence/B-manual-cancel.json`。

### 建议的最小修复（给 Codex，按代价排序）

1. **启动时补一次"孤儿 validating"对账**：扫描 `subtask.status='validating'` 且其最新 run 已终态、且没有活跃 claim 的子任务 → 把 task/subtask 标为 `failed`（`PROCESS_CRASHED`，"validation interrupted；review the workspace before retry"），并释放占位。这样至少不会"静默卡死"。
2. **让测试阶段有自己的 claim**：注册测试也写一条 claim（含测试进程组 pid），崩溃后 `reconcileExpired` 就能像处理模型 run 一样处理它，也才能在恢复时安全地判断"测试进程是否还在"。
3. **暴露状态**：`meta` 里增加 `stuckValidating` 计数（或 `needsAttention`），让 UI 至少提示"有任务需要人工处理"。

## 四、场景 C：模型进程被杀 → 收敛为失败（通过，但策略值得确认）

```
05:56:32 抓到 modelTurnLive（run=running，providerSessionId 已建立，pgid=8440 是真实 codex 进程）
05:56:32 kill -9 -8440
05:56:38 run = failed / PROCESS_CRASHED
         subtask IMPL = failed(attempt 1)
         task = failed / PROCESS_CRASHED
         slot = 0，仓库未变
```

**行为是正确的**（不把未知崩溃当成功），但有两点要明确：

- **不会自动重试**：`PROCESS_CRASHED` 的 `retryable=false`，所以虽然 `maxAttempts=2`，attempt 2 不会发生。这与交接报告"崩溃运行隔离、不盲目续跑"的设定一致，但意味着**一次瞬时进程崩溃就会让任务失败**，需要人工 retry。
- **没有 `interrupted` 状态**：进程组被杀后 run 直接 `failed`，而不是 `interrupted`。`interrupted` 只在"控制器失联/租约过期"时出现。

## 五、一条结构性说明（影响以后所有"进程组"判断）

不同 provider 的 `process_group_id` 语义不一样：

| provider | claim 里的 `process_group_id` | 含义 |
|---|---|---|
| Codex CLI | 真实 `codex exec` 子进程 pid | 可以 `kill(-pgid)` 验证/终止 |
| DeepSeek / Gemini 等 API 型 | **控制器自己的 pid**（`deepseek/runtime.ts` 里 `onSpawn(runId, process.pid)`） | 没有模型子进程；`store.ts` 里用 `!== process.pid` 避免恢复过程误杀自己 |

所以对 API 型 provider：
- "进程组已验证停止" 实际上说的是"**旧控制器**已经不在了"，不是"模型进程停了"；
- 测试子进程（`codex sandbox` 包装 + 测试脚本）**不在 claim 里**，这正是场景 B 卡死的根因之一。
