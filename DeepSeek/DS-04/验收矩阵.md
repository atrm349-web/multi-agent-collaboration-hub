## 3. 必须先说清的两个限制

1. **f02-r2 的证据早于当前前端快照。** `controlled-chrome-f02-r2.json` 记录 `app.js e1652a7c…`，而现在生效的是 `a0c69a3c…`（17:28 UI 重做）。所以即使它写着 PASS，也**不能**直接当成"当前界面的验收结果"——UI 布局变了，按钮位置/文案/可见性都可能变。
2. **`real-http.json` 停在 `waiting_approval`。** 它的 `detail.task.status` 是 `waiting_approval`、`progressPct 48`、1 个 pending approval。README 说的"succeeded"由 `restart-approval-proof.ts` 完成，但该脚本的输出（`final-evidence.json`）没有随交付归档。`browser.json` 里的 SUCCEEDED 页面是独立证据，能补上"页面终态"，但补不了"DB 终态"。


## 3.5 执行环境约束（本轮实测，直接影响 DS-04 由谁执行）

| 能力 | 受限沙箱（我的默认） | 完全访问（需逐次审批） |
|---|---|---|
| Hub 控制器 / HTTP / SQLite | ✅ 可启动、可用 | ✅ |
| `codex sandbox`（注册测试、质量门） | ❌ `sandbox_apply: Operation not permitted`（退出码 71） | ✅（DS-01 已实测） |
| Google Chrome headless + CDP | ❌ `sandbox initialization failed: Operation not permitted`，Chrome 崩溃 | ✅（`/json/version` 返回 `Chrome/156.0.8078.80`） |
| `ps` / `top` | ❌ Operation not permitted | 未测（`pgrep`、`lsof`、`footprint` 在受限下可用） |

**推论**：DS-04 里任何"浏览器点击级"证据（截图、DOM 断言、按钮流程）都**不能在受限沙箱内产出**，必须由用户在自己的 Terminal 执行，或对那一次运行授权完全访问。这不是脚本问题，是 Chrome 自身要初始化它的 seatbelt 沙箱。

## 4. DS-04 执行时要产出什么

一份**同一源码哈希下**的报告，包含：

1. 场景 1–10 的逐项结果，每项写明：执行方式（真实/受控）、输入、结果、证据路径。
2. 至少一条**真实模型**的成功路径，且终态是 `succeeded`，附带：task/subtask/run/validation/approval 的 DB 快照 + 页面截图 + 下载文件与 `artifact.sha256` 的比对。
3. 至少一条**真实模型**的失败返工路径（来自 DS-02）。
4. 其余按钮类场景若未在真实任务中重测，**保留其受控分类**，不得升级为"已验收"。
5. 明确写出"本轮未覆盖"的边界（Windows、跨厂商、长稳、崩溃续跑）。

## 5. 与 DS-02 的衔接

DS-02 的 S1 恰好补齐场景 2 与场景 1 的缺口：它会走完 `create → attempt1 失败 → rework → attempt2 → FINAL-REVIEW → 人工审批 → succeeded`，并且我会把 **DB 终态**（task/subtask/run/validation/approval/artifact）导成 JSON 归档，正好补上 `real-http.json` 缺的那一段。
