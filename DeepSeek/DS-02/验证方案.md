# DS-02 验证方案：真实模型失败与自动返工闭环

- 提出方：DeepSeek　日期：2026-11-03　状态：**待执行授权**（方案先行，按交接报告第 10 节要求）
- 验收对象：`backend/agetor` 基线 `9f56aa45…`，`HubService` + `docker`-free 本地真实 Codex CLI
- 关键前提：**planner 会被显式绕过**（用 `plannedSubtasks` 直接建任务），provider / 注册测试 / 独立审查 / 人工审批全部真实。这与"受控故障替身"有本质区别——失败来自真实模型产出的代码没通过真实测试，不是注入的假失败。

## 1. 要证明的事

1. 真实模型第一次实现**未满足**固定验收标准时，`execute()` 会依据**真实测试退出码**触发返工，而不是靠模型自称成功。
2. 第二次 attempt 能拿到第一次的失败证据（返工原因），并在其基础上修复。
3. 返工后重测通过 → 独立审查（**另一个 provider session**）→ 人工审批 → Task `succeeded`。
4. 返工过程中旧产物/旧审批不会"复活"；attempt 上限生效；原仓库 HEAD 不变。

## 4. 任务设计：如何让"第一次真实实现"不达标

被测需求（写进 repo 的 `README.md`，作为模型能看到的唯一规格）：

> 实现 `src/amount.mjs`，导出 `formatAmount(minorUnits)`，把整数分转换成给人看的人民币金额字符串。

**goal 故意不完整**（这是设计，不是伪造）：不提千分位、不提负号位置、不提非法输入。验收脚本 `check.mjs` 断言更严格：

| # | 断言 | 首次失败概率 |
|---|---|---|
| 1 | `formatAmount(1234) === '¥12.34'` | 低 |
| 2 | `formatAmount(5) === '¥0.05'` | 中 |
| 3 | `formatAmount(123456) === '¥1,234.56'`（千分位） | **高** |
| 4 | `formatAmount(-1234) === '-¥12.34'`（负号在符号前） | **高** |
| 5 | `formatAmount(1.5)` 抛 `RangeError` 且 `message` 含 `INVALID_AMOUNT` | 中 |

失败时 `check.mjs` 把 `expected / actual` 逐条打到 stderr 后 `exit 1`。这段 stderr 会进 `validation` 的 `exitCode` 证据与 `rework_instruction.content`，模型第二次能看到期望值——**这正是"真实返工"该有的信息通道**。

**三级 forcing（若首次直接通过就升级，按交接报告要求如实记录）**：

- A（默认）：上表，goal 只说"带人民币符号、两位小数"。
- B：A 通过则加入 `sumAmounts(list)` 需求，但 goal 完全不提，只出现在验收里 → 首轮几乎必失败（`sumAmounts is not a function`），且失败信息给出了调用样例。
- C：B 仍通过则加"`NOTES.md` 必须含 `## 舍入策略` 小节并写明 half-up"这类文档型验收。

每次升级都在报告里明确写：「第 N 次尝试首轮直接通过，真实结果已记录，随后升级设计」。**不会把受控故障写成真实失败，也不会把通过写成失败。**

## 5. 场景与步骤

### 场景 S1：真实失败 → 自动返工 → 审查 → 审批 → succeeded（主场景）

1. 准备 `repo/`、`owner-tests/`、`runtime/`，`git init` + baseline commit；记录 `git rev-parse HEAD` 与 `git status`。
2. 启动：`PATH=<codex-bin>:$PATH bun scripts/start-hub.ts <abs>/config.json`（后台作业，记录 PID/端口）。
3. `POST /api/v1/tasks`，带 `plannedSubtasks`：
   - `S1-IMPL`：stage=`implementation`，`dependsOn=[]`，1 条 criterion（`testProfileId: acceptance`）；
   - 系统自动追加 `FINAL-REVIEW`（review stage，绑 task-level criteria）。
   同时记录 task id / version。
4. 轮询 `GET /api/v1/tasks/{id}` 直到出现 `attempt=2` 的 `retry_wait`（或任务失败）。抽取：两个 run 的 `id/subtaskId/attempt/status/exitCode/providerSessionId`、两条 validation（第一条 `failed` 且 `exitCode=1`）、`rework_instruction` 消息内容。
5. attempt 2 通过后等待 `FINAL-REVIEW` 进入 `waiting_approval`；由**用户在 LIVE UI 点击审批**（或按第 7 节授权代执行）。
6. 审批后校验：Task `status=succeeded`、`progressPct`、`artifactCount`、approval `status=approved`、`actionDigest` 与 delivery digest 一致。
7. 收尾：SIGINT 停服；只读导出 SQLite（`bun` 或 `python3 sqlite3`，只读连接）；校验 `repo/` HEAD 与 baseline 一致、工作区干净。

### 场景 S2：审批拒绝 → 返工 → 旧审批失效（覆盖"旧审批/旧产物不复活"）

在 S1 通过后的同一 repo 上新建任务 S2（或 S1 改为 reject 一次再 approve）：

1. FINAL-REVIEW 通过 → 审批 pending，记录 `approval.id/version/actionDigest`。
2. **reject**（用户点击或授权代执行）→ 走 `subtaskAction(rework)` → attempt 2。
3. 断言：旧 approval `status=rejected`；第一次 delivery 的 artifact 不再满足 `captureFinalDelivery`（`outputArtifactIds` 已清空 → `ACCEPTANCE_FAILED`）；新的 approval `actionDigest ≠` 旧值；旧产物仍可下载但**不进入新审批的 `artifactRefs`**。
4. 新 attempt 通过 → 新审批 → approve → succeeded。

### 场景 S3：attempt 上限（负向，明确标注为受控设计）

在临时 repo 上注册一个**必然失败**的 criterion（`check.mjs` 断言一个不存在的导出），验证：

- attempt 1 失败 → 返工 → attempt 2 失败 → `rework()` 抛 `UNSUPPORTED_TRANSITION: retry budget exhausted` → Task `failed`，`error.code` 记录、**不产生任何 pending 审批**。
- 第三次不会被执行（run 表只有 2 条）。

## 8. 开工前要 Codex 回答的两个问题

- **Q1**：`rework()` 清空 `outputArtifactIds` 但把 `artifactRefs` 放进消息——第二次 attempt 的 prompt 里只有 id，没有内容。这是"防止旧产物复活"的设计意图，还是想让模型能读到旧 diff？前者我按现状验收；后者需要改 `execute()` 的 prompt 构造，属于后端改动，需你实施。
- **Q2**：`maxAttempts=2` 是全局默认。DS-02 的 S1 依赖"恰好两次"能过。如果第一次失败信息不足以修复，任务会直接 `failed`（因为第 2 次也失败就不再返工）。你是否同意本实验**保持 maxAttempts=2 不调**，以验证默认策略下的真实行为？若失败，我会把"两次不够"作为结论提出，而不是改配置掩盖。

## 9. 风险与止损

| 风险 | 处理 |
|---|---|
| 真实模型第一次就通过 | 如实记录，升级 forcing 设计（A→B→C），不伪造失败 |
| 两次都不通过 → 任务 failed | 保留全部证据，作为"默认重试预算不足"的真实结论上报 |
| CLI 崩/超时/断网 | 记录 run 状态；若是 `retryable` 则观察自动返工路径；不手工改数据库 |
| 审批 digest 对不上 | 说明产物在审批期间被改动，保留证据，不当成通过 |
| 时间/额度超支 | 先只做 S1；S2/S3 视 S1 结果与额度再排 |
